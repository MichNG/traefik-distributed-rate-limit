# 16. Бенчмарк: накладные расходы и p99 (методика и результаты)

Пункт бэклога «бенчмарк p99 при 1k/5k RPS». Измерения сделаны в двух слоях:
**микробенчмарки middleware без docker** (`bench_test.go`) и **e2e-харнесс**
(`hack/bench/`) на реальном Traefik + Redis + бэкенд в docker.

Дата прогонов: 2026-11-27. Ничего из этого не запускается в CI (нужны docker и
стабильная машина); команды ниже воспроизводимы вручную.

---

## 1. Методика

### 1.1. Микробенчмарки (`bench_test.go`)

`go test -bench . -benchmem` — офлайн, без docker: в процессе теста поднимается
минимальный RESP-сервер (`benchRedisServer`), который отвечает ровно на то, что
шлёт клиент плагина (`SELECT`, `SCRIPT LOAD`, `EVALSHA`), и отдаёт заранее
заготовленный ответ token-bucket. Скрипт Lua при этом **не исполняется** —
измеряется путь плагина: разбор конфигурации запроса, выбор источника,
лимитер, RESP-кодек, пул соединений, round trip по loopback, запись ответа.

Сценарии — два интересных исхода middleware, каждый на 1 и 64 горутинах, с
`X-RateLimit-*` и без:

| сценарий | конфигурация |
| :--- | :--- |
| `allow` | лимит заведомо выше нагрузки, store отвечает «разрешено» |
| `allow_headers` | то же + `responseHeaders: true` |
| `deny` | store отвечает «отказано» → 429 |
| `deny_headers` | то же + `responseHeaders: true` |
| `next` (базовая линия) | сам `ServeHTTP`-приёмник без плагина |

`TestBenchScenariosMatchTheirNames` (в том же файле) проверяет, что сценарии
действительно возвращают 200/429 и включают/выключают заголовки, а store
реально вызывается (иначе бенчмарк молча мерил бы не то).

Если задан `REDIS_ADDR`, дополнительно исполняется `BenchmarkServeHTTPRealRedis`
— те же сценарии против настоящего Redis (в нём Lua исполняется по-настоящему,
`deny` получается лимитом `1/1s`).

Что важно про цифры: `B/op` и `allocs/op` в Go считаются по всему процессу,
поэтому fake-сервер написан без аллокаций (reusable-буферы, `ReadSlice`,
`bytes.EqualFold`) — иначе аллокации тестового двойника попали бы в отчёт
плагина. Контроль: офлайн-цифры аллокаций совпадают с прогоном против реального
Redis (37–38 allocs/op на «allow»).

### 1.2. e2e-харнесс (`hack/bench/`)

```
hack/bench/
├── docker-compose.single.yaml   # Traefik v3.5 + whoami + Redis (Redis не публикуется)
├── docker-compose.dual.yaml     # два Traefik + один общий Redis
├── loadgen/main.go              # генератор нагрузки, только stdlib
└── run.sh                       # обвязка: стенды, прогоны, разбор, таблица
```

`run.sh`:

* поднимает стенды `docker compose` (хост-порты Traefik `18000`/`18080`, у второго
  инстанса `18001`/`18081`; **Redis портов на хост не имеет**);
* собирает `loadgen` под хост и под `linux/arm64`, второй экземпляр запускается
  сервисом `loadgen` (образ `traefik:v3.5`, тот же, что у стенда — новых образов
  не тянется) **внутри compose-сети**, чтобы убрать из замера проброс портов
  docker Desktop;
* меняет динамический конфиг (file provider, hot reload), ждёт готовности,
  прогоняет нагрузку, снимает с логов Traefik строки ошибок стора и счётчик
  соединений Redis, и печатает сводную таблицу;
* каждый прогон — `warmup 2s` + `duration 10s` (кейсов 10, вся обвязка ~3 минуты).

`loadgen` измеряет **клиентскую** задержку (соединение переиспользуется: запрос,
чтение тела) и печатает RPS, p50/p90/p95/p99/max/mean, разбивку по кодам и по
URL (для двух инстансов).

Все прогоны, кроме специально оговорённого кейса 8, идут с
`store.redis.poolSize` = `maxActiveConns` = числу воркеров (32): иначе числа
описывали бы не плагин, а churn соединений (см. §5.3).

## 3. Микробенчмарки: стоимость запроса

`go test -run '^$' -bench 'BenchmarkServeHTTP$|BenchmarkNextHandler' -benchmem -benchtime=1s ./`

### 3.1. Fake store (без docker)

| сценарий | ns/op | B/op | allocs/op |
| :--- | ---: | ---: | ---: |
| `allow/c1` | 28 999 | 1 481 | 37 |
| `allow/c64` | 10 661 | 1 484 | 37 |
| `allow_headers/c1` | 30 391 | 1 658 | 48 |
| `allow_headers/c64` | 10 526 | 1 658 | 48 |
| `deny/c1` | 30 256 | 1 505 | 38 |
| `deny/c64` | 10 493 | 1 505 | 38 |
| `deny_headers/c1` | 30 368 | 1 673 | 48 |
| `deny_headers/c64` | 10 403 | 1 673 | 48 |
| `next/c1` (без плагина) | **29.97** | 18 | 2 |
| `next/c64` (без плагина) | **10.63** | 18 | 2 |

Читается так:

* цена middleware = один round trip к Redis (у fake-стора — loopback) + разбор
  заголовков/источника: **~29 µs на запрос при c=1**, ~10.5 µs при c=64
  (там ns/op — это уже пропускная способность, а не задержка);
* включение `responseHeaders` видно по аллокациям — **+11 allocs/op и +177 B/op**
  (шесть значений заголовков), по времени — в пределах шума (±3 %);
* «allow» и «deny» по стоимости одинаковы: middleware не зависит от исхода.

### 3.2. Реальный Redis (`REDIS_ADDR=127.0.0.1:6379`)

| сценарий | ns/op | B/op | allocs/op |
| :--- | ---: | ---: | ---: |
| `allow/c1` | 139 187 | 1 538 | 38 |
| `allow/c64` | 21 046 | 1 540 | 38 |
| `allow_headers/c1` | 138 018 | 1 713 | 49 |
| `allow_headers/c64` | 33 255 | 1 717 | 49 |
| `deny/c1` | 143 090 | 1 563 | 36 |
| `deny/c64` | 32 165 | 1 567 | 36 |
| `deny_headers/c1` | 125 124 | 1 731 | 45 |
| `deny_headers/c64` | 20 326 | 1 734 | 45 |

Здесь видно главное: с настоящим Redis цена запроса определяется **сетью до
стора** (в этом прогоне клиент на хосте, Redis — за пробросом порта Docker
Desktop): ~140 µs при c=1. На c=64 разброс (20–33 µs) объясняется тем, что
упирается уже сам проброс порта к Redis, а не плагин. Аллокации те же, что с
fake-стором, — кодек и лимитер работают идентично.

## 4. e2e: один и два инстанса Traefik

`BENCH_WORKERS=32 ./hack/bench/run.sh` (каждый кейс: 2 c прогрев + 10 c замер).

| кейс | RPS | p50, ms | p95, ms | p99, ms | 200 | 429 | ошибок стора |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `single/limit=0` (контроль: плагин выключен) | 6 669 | 4.16 | 10.68 | 14.63 | 66 693 | 0 | 0 |
| `single/allow` | 6 446 | 4.21 | 10.77 | 14.73 | 64 463 | 0 | 0 |
| `single/allow+headers` | 6 486 | 4.19 | 10.69 | 14.75 | 64 858 | 0 | 0 |
| `single/limited(100/s)` | 17 832 | 1.62 | 3.21 | 4.43 | **1 001** | 177 321 | 0 |
| `net/allow` | 7 227 | 3.70 | 10.20 | 14.05 | 72 267 | 0 | 0 |
| `net/allow+headers` | 7 342 | 3.68 | 9.93 | 13.44 | 73 423 | 0 | 0 |
| `net/limited(100/s)` | 24 331 | 1.09 | 2.93 | 4.13 | **1 000** | 242 310 | 0 |
| `net/allow (default pool) #1` | 7 270 | 3.71 | 10.03 | 13.62 | 72 703 | 0 | 0 |
| `net/allow (default pool) #2` | 18 503 | 0.75 | 7.06 | 11.27 | 47 032 | 137 996 | **1** |
| `dual/limited(100/s)+headers` | 23 122 | 1.10 | 3.27 | 4.64 | **1 001** | 230 217 | 0 |

«single» — клиент на хосте (через порт 18000), «net» — клиент контейнером в
compose-сети; «limit=0» — плагин в цепочке, но выключен (`limit: 0` → сразу
`next`), это база для host-замеров.

### 4.1. Кластерный лимит (два инстанса, один Redis)

`dual/limited`: лимит 100/с на **обоих** инстансах, нагрузка поровну
(round-robin по двум URL), `responseHeaders: true`:

* разрешено **1 001** запрос за 10 c — ровно `limit × duration = 1 000`, а не
  2 000+: инстансы делят один бакет;
* разбивка по инстансам: **496** и **505** — сумма 1 001;
* в Redis один ключ на источник: `rate:distributed-ratelimit@file:bench-user`.

### 4.2. Стоимость `responseHeaders`

| | без заголовков | с заголовками | разница |
| :--- | ---: | ---: | ---: |
| `single/allow` (хост) | 6 446 RPS / p50 4.21 ms | 6 486 RPS / p50 4.19 ms | в пределах шума |
| `net/allow` (в сети) | 7 227 RPS / p50 3.70 ms | 7 342 RPS / p50 3.68 ms | в пределах шума |
| микробенчмарк, c=1 | 28 999 ns / 37 allocs | 30 391 ns / 48 allocs | **+11 allocs/op, +177 B/op, время ±3 %** |

Вывод: заголовки практически бесплатны; их цена — 11 аллокаций на запрос
(шесть `Header().Set` плюс форматирование чисел), что для любого разумного RPS
несущественно.

## 5. Где узкое место

### 5.1. На «allow»-пути в этом окружении упирается бэкенд, а не плагин

Разложение по слоям (все — клиент внутри сети, 32 воркера):

| что измеряем | RPS | p50, ms |
| :--- | ---: | ---: |
| `whoami` напрямую, без Traefik | 7 386 | 3.99 |
| Traefik + `whoami`, плагин выключен (`limit: 0`) | 7 102 | 4.23 |
| Traefik + плагин + `whoami` (`net/allow`) | 7 227 | 3.70 |

То есть ~4 ms и ~7 k RPS — это потолок связки «контейнер-бэкенд + планировщик
VM Docker Desktop»; плагин на этом фоне неотличим от нуля (разница в пределах
разброса прогонов). Собственная цена плагина — это §3: один round trip к Redis
(29 µs на loopback при c=1, 140 µs до контейнера Redis через проброс портов).

### 5.2. «Deny»-путь дешевле и масштабируется лучше

Когда решение — 429, плагин не зовёт `next`: `net/limited` даёт 24 331 RPS при
p50 1.09 ms против 7.2 k RPS на «allow». Это ожидаемо (бэкенд не участвует) и
важно помнить при оценке «RPS под лимитом»: запрещающий трафик обслуживается в
3–4 раза быстрее разрешающего.

### 5.3. Настоящее узкое место при конкурентной нагрузке — churn соединений при маленьком `poolSize`

Кейс 8 (`net/allow` с дефолтным пулом, два прогона подряд) и счётчик
`total_connections_received` в Redis:

| прогон | новые соединения к Redis за 12 c | результат |
| :--- | ---: | :--- |
| `poolSize`/`maxActiveConns` = 32 | **32** | 72 703 × 200, 0 ошибок |
| маленький пул (`poolSize: 5`) #1 | **15 733** | 72 703 × 200, 0 ошибок |
| маленький пул #2 (сразу следом) | 12 403 | 47 032 × 200 + **137 996 × 429**, ошибка стора |

> Прогоны сделаны до 1.1.0, когда `poolSize` по умолчанию равнялся 5. В 1.1.0
> дефолт изменён: незаданный `poolSize` теперь равен `maxActiveConns`, поэтому
> «из коробки» прогон ведёт себя как строка «= 32», а маленький пул остаётся
> только явным выбором оператора.

Ошибка из лога Traefik дословно:

```
ERROR no rate limit decision from the store on node "redis:6379": evaluating the
token bucket: dialing redis:6379: dial tcp 172.19.0.3:6379: connect: cannot
assign requested address
```

`cannot assign requested address` — исчерпание эфемерных портов в контейнере
Traefik: при `poolSize: 5` и 32 одновременных запросах соединение почти каждого
запроса закрывается вместо возврата в пул (в `put` пул переполнен, соединение
закрывается), и десятки тысяч новых TCP-соединений за минуту упираются в
`TIME_WAIT` + размер диапазона эфемерных портов. Дальше срабатывает breaker
(3 отказа / 15 c), и при `denyOnError: true` **все** запросы становятся 429 —
внешне это выглядит как «лимит сломался», хотя причина в пуле.

Лечение (проверено): `store.redis.poolSize` (и `maxActiveConns`) ≥ ожидаемого
числа одновременных запросов — 32 на 32 воркера дают ровно 32 соединения и ноль
отказов. **Сделано в 1.1.0:** незаданный `poolSize` больше не фиксирован на 5, а
равен `maxActiveConns` (`internal/redis/client.go`), т.е. соединения возвращаются
в пул, а не закрываются; тест — `TestClientConfigDefaultsKeepIdleCapacity`. Явно
заданный маленький `poolSize` по-прежнему работает и воспроизводит деградацию:
это осознанный выбор оператора.

### 5.3.1. Повторный прогон после изменения дефолта (1.1.0)

Тот же e2e-прогон после того, как незаданный `poolSize` стал равен
`maxActiveConns` (кейс «default pool», по-прежнему без явных настроек пула):

| прогон (default pool) | новые соединения к Redis | результат |
| :--- | ---: | :--- |
| #1 | **32** | 98 543 × 200, 0 × 429, 0 ошибок стора, 9 854 RPS / p99 10.5 ms |
| #2 (сразу следом) | **1** | 96 698 × 200, 0 × 429, 0 ошибок стора, 9 670 RPS / p99 10.9 ms |

То есть с новым дефолтом соединения возвращаются в пул, а не закрываются:
портовый churn исчез, breaker не открывается, деградации из §5.3 больше нет.
Полный прогон (10 кейсов) в тот же день: «allow» ~8.1–9.8 k RPS, «deny»
~21–32 k RPS, кластерный лимит 1 001 при `limit × duration = 1 000`
(484 + 516 по инстансам), 0 ошибок стора во всех кейсах.

### 5.4. Redis — не узкое место

`redis-benchmark` в том же контейнере: **186 916 SET/s**, **216 606 GET/s**
(c=50). Плагин на запрос делает ~4 команды Redis (`EVALSHA`, а внутри скрипта
`TIME`, `GET`, `SET`), т.е. при 7 k RPS это ~28 k ops/s — запас более чем
шестикратный. Упираться в Redis этот стенд начинает только при «пакетной»
нагрузке на десятки тысяч RPS, и раньше сработает §5.3.

## 6. Оговорки

* **Клиентская задержка.** `loadgen` меряет то, что видит клиент, включая
  проброс портов Docker Desktop для host-прогонов. База проброса: `whoami`
  напрямую через порт 18010 — 6 824 RPS / p50 4.37 ms при 32 воркерах, т.е.
  host-прогоны (§4) этим и ограничены.
* **Одна VM.** Все контейнеры (Traefik, whoami, Redis, loadgen) делят одну
  виртуальную машину Docker Desktop без CPU-лимитов; абсолютные RPS — это
  характеристики стенда, а не «сколько выдержит сервер». Сравнивать между собой
  можно только строки одной таблицы.
* **Один прогон на кейс.** Повторов нет: p99 на 10-секундном окне — оценка, а не
  статистически устойчивая величина; разброс между прогонами ~±5–10 % (видно по
  `allow` vs `allow+headers`).
* **Fake store не исполняет Lua.** Микробенчмарки не включают время исполнения
  скрипта на сервере; e2e (§4) включает, но там его вклад не отделён от сети.
* **`limit=0` как контроль** — плагин в цепочке выключен, но это не «чистый
  Traefik»: остаётся вызов `ServeHTTP` middleware (несколько десятков ns по §3).
* **Что не измерялось:** TLS/mTLS к Redis, Sentinel (обнаружение мастера не на
  горячем пути, но добавляет фоновую подписку), Redis Cluster, несколько
  источников (кардинальность ключей), нагрузка с разными лимитами на источник,
  длительные прогоны на устойчивость (утечки/деградация за часы).
* **Логи.** Traefik запущен с `log.level=INFO`; отладочные сообщения плагина
  (уровень DBG) выключены, чтобы логирование не влияло на замер.

## 7. Как воспроизвести

```bash
cd plugin

# 1) микробенчмарки, офлайн
go test -bench . -benchmem -benchtime=1s ./            # fake store
docker run -d --name bench-redis -p 6379:6379 redis:7  # опционально
REDIS_ADDR=127.0.0.1:6379 go test -bench BenchmarkServeHTTPRealRedis -benchmem ./ 

# 2) e2e (docker), ~3 минуты, 10 кейсов
./hack/bench/run.sh
BENCH_WORKERS=64 BENCH_DURATION=15s ./hack/bench/run.sh   # более тяжёлый профиль
BENCH_KEEP=1 ./hack/bench/run.sh                          # сохранить сырые выводы кейсов
```

Сырые выводы прогона 2026-11-27 — в таблицах §3 и §4 (сняты приведёнными
командами); стенды `run.sh` гасит сам, Redis на хост не публикуется.
