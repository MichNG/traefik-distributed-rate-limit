# Options: every variant, with a stand that proves it

`example/options/` contains one example per option of the [Options table in the
README](../README.md#options), in every variant the option accepts, and
`hack/options/run.sh` loads the whole directory in a real Traefik to prove that
each example is actually built.

```bash
# from the plugin root; ports 29000/29080 by default, Redis is not published
make integration-options              # or: HTTP_PORT=29000 API_PORT=29080 ./hack/options/run.sh
```

The stand asserts three things:

1. every *positive* middleware of the directory is created (the Traefik API
   reports it enabled, with no error) - **73** middlewares;
2. every *negative* configuration is refused with the documented message - **20**
   middlewares, and the router that uses such a middleware answers `404`;
3. **72** behavioural checks: the shape of a drain, the bucket key of every
   source criterion, the whitelist bypass, the credential variants, the database
   index, the legacy warnings and the store errors.

Artifacts land in `artifacts/options/` (`summary.txt`, the per-middleware JSON,
the request traces, the Redis keys, the Traefik log, the generated fixtures) and
are also collected when the stand fails.

## How the stand is wired

* `docker-compose.options.yaml` runs Traefik v3.5 with the file provider in
  **directory mode** (`--providers.file.directory=/etc/traefik/options`), so every
  file of `example/options/` is a dynamic configuration. The plugin is mounted as
  a local plugin.
* Two Redis instances: `redis` (no credentials, the case of most examples) and
  `redis-auth` (two ACL users, for the credential examples). Neither is published
  on the host.
* The TLS fixtures (`redis-ca.crt`, `client.crt`, `client.key`) are generated by
  the script with `openssl` into `artifacts/options/certs/` and mounted at
  `/etc/traefik/certs`, where the path variants of `06-store-tls.yaml` point.
* `log.level: DEBUG` is required to see the plugin's configuration warnings: a
  Yaegi plugin writes them to the interpreted stdout, which Traefik reports at
  debug level.
* `forwardedHeaders.insecure: true` on the entry point makes the hand-written
  `X-Forwarded-For` of the checks visible to `ipStrategy` (production should use
  `trustedIPs`; see the comment in `example/traefik-options.yaml`).
* `10-routers.yaml` references every middleware of the directory once. It is not
  decoration: **Traefik builds a middleware only when a router uses it**, so an
  unreferenced middleware is never instantiated and its configuration error would
  go unreported (see finding 1 below). The file also gives every middleware a
  stable URL, `http://localhost:29000/mw/<middleware name>`, which is what the
  behavioural checks use.

## The examples

`variants` lists what the file covers; `example` is the middleware name inside
`example/options/<file>.yaml`, unless a section is named.

### Rate

| Option | Variants | Example | Verified by |
| :--- | :--- | :--- | :--- |
| `limit` | default (`0`, rate limiting off), `0` explicit, a plain `100` | `01-rate.yaml`: `rate-defaults`, `rate-zero-limit`, `rate-limit-100` | 20 requests all `200` and **no** bucket key for `limit: 0` |
| `period` | `500ms`, `1m`, legacy whole seconds (`"5"`) | `rate-period-500ms`, `rate-period-1m`, `rate-period-whole-seconds` | drain `1 × 200 → 429`, then `200` again after the 500 ms refill |
| `burst` | omitted (defaults to `1`), explicit `10`, `limit` + `burst` together | `rate-burst-default`, `rate-burst-explicit`, `rate-limit-burst-combo` | drain `1 × 200 → 429` and `10 × 200 → 429` (a fresh bucket holds `burst` tokens) |
| `denyOnError` | `true` (and the default) and `false`, both against an unreachable store | `rate-deny-on-error-true`, `rate-deny-on-error-false` | `3 × 429` and `3 × 200` |
| `responseHeaders` | `true` (`X-RateLimit-Limit/Period/Remaining/Reset`) and `false` | `rate-headers-true`, `rate-headers-false` | the `429` carries `X-RateLimit-Limit: 1`, the other one carries no `X-RateLimit-*` |

### Deprecated v1 keys

`07-legacy.yaml` covers the flat keys the README documents as deprecated:
`average`, `redisAddress`, `redisDb`, `redisPassword`, `redisConnectionTimeout`,
`breakerThreshold`, `breakerReattempt`. `legacy-all-flat-keys` uses all of them
(the bucket ends up in database 2, which proves `redisDb` was applied),
`legacy-minimal` and `legacy-timeout-only` use a subset, and
`legacy-new-keys-win` shows that the new `store.redis.*` keys win over the legacy
ones of the same middleware (with the "ignored because …" warning). Warning
messages: see finding 3 (fixed: they are all logged now).

## Findings

Building this catalogue turned up five things worth knowing. Findings 2, 3 and 4
were **fixed** in the revision that followed the audit (the stand now asserts the
fixed behaviour); 1 and 5 are properties of the platform the catalogue has to
live with.

1. **Traefik builds a middleware only when a router uses it.** A middleware that
   no router references is never instantiated: the API reports it as `enabled`
   even when its plugin configuration is invalid, so a broken but unused
   middleware goes unnoticed until something routes to it. Checked on the stand:
   `bad-negative-limit` is `enabled` while no router references it, and becomes
   `disabled` with `limit must be >= 0 …` as soon as one does. Consequence for
   this directory: `10-routers.yaml` (or the fact that a middleware must be used)
   is what makes the checks meaningful.
2. **`store.redis.cluster` in every shape — fixed.** Traefik's plugin
   configuration decoding flattens an empty mapping to the empty string, so with a
   typed field an empty `cluster:` was refused by the decoder
   (`'store.redis.cluster' expected a map, got 'string'`) instead of producing the
   plugin's own message. The field now accepts any shape and the validation is
   what answers, so `cluster: {}`, `cluster: {enabled: true}` and the flattened
   `cluster: ""` all report the documented
   `store.redis.cluster is not supported yet`; the stand asserts the message for
   both spellings, and `TestClusterIsRejectedInEveryShape` covers the four shapes.
3. **Every deprecation warning is logged now — fixed.** `normalize()` returns one
   warning per folded legacy key, but `newRateLimit` logged them with
   `warnf("%s", warning)` and the plugin logger throttles on the *format string* -
   the constant `"%s"` - so only the first warning of a middleware survived the
   five-second window. `warnMessage` now throttles on the rendered message (the
   flood control stays: a repeated identical warning is still dropped once), so a
   middleware with six legacy keys reports all six. The stand asserts each of
   them, and `TestEveryDeprecationWarningIsLogged` / `TestLoggerThrottlesPerMessage`
   pin the behaviour down.
4. **A dial failure rotates `store.redis.endpoints` now — fixed.** The endpoint
   list is rotated by `StaticProvider.Failure`, which `DoRaw` used to call only
   for failures *after* a connection was established (`c.get` errors returned
   immediately), so an endpoint whose host did not resolve was selected forever:
   each request retried it and, with `denyOnError: true` (the default), every
   request was a `429`. Two changes: `DoRaw` reports a `get` failure to the
   provider (the request is then retried on the next endpoint), and
   `IsMasterFailoverError` classifies the error through `errors.As` - a plain
   type assertion missed every *wrapped* network error - while explicitly
   excluding the context deadlines of a saturated pool and a cancelled request,
   which say nothing about the node. Measured on the stand: a dead-first
   `endpoints: [redis-nowhere:6379, redis:6379]` list answers `200`, and the
   bucket is found on the healthy endpoint. Covered by
   `TestDialFailureRotatesToTheNextEndpoint`, `TestDialFailureRotatesOnDNSFailure`
   and `TestIsMasterFailoverErrorIsWrapperAware`.
5. **The client address of a request that arrives through a published port is the
   docker gateway**, not `127.0.0.1` (`192.168.65.1` on Docker Desktop, `172.x` on
   a Linux runner): that is why the checks of the source criteria that use the
   connection address assert on a pattern instead of an address, and why the
   `X-Forwarded-For` examples need a *trusted* header (the stand sets
   `forwardedHeaders.insecure`, production needs `trustedIPs`).

A related behaviour worth writing down, although it matches the documentation: a
fresh bucket holds `burst` tokens, not `limit` - `limit: 5, burst: 10` passes 10
requests and rejects the 11th.
